# Authentication runtime

This closed research system uses ASP.NET Core JWT bearer validation and RSA-SHA256 grants issued by Identity. User accounts and password hashes live only in `identity_db`; Identity never stores plaintext passwords. Registration allows Rider or Driver roles. Actor IDs are server-generated account UUIDs, and Driver routes bind them to the durable Driver `user_id`, which differs from `driver_id`.

For local development or disposable CI, run `python3 scripts/security/init-local-auth.py` before Compose startup. It requires OpenSSL and writes a fresh RSA key pair and random service credentials only to ignored `.env`. Existing complete credentials are preserved. `.dockerignore` excludes `.env` and `secrets/`. Never run `docker compose config` without `--quiet` when credentials are populated, or upload rendered configuration/environment dumps.

Only Identity receives `Auth__PrivateKeyBase64`. Gateway, Trip, Driver and Matching require `Auth__PublicKeyBase64`; missing keys prevent startup. Identity verifies that its signing and validation keys match. All validators require signature, RS256, issuer, audience, expiry and lifetime; clock skew is 15 seconds. The issuer is `ride-hailing-identity` and audience `ride-hailing-api` in Compose.

Public Gateway endpoints are `POST /auth/register`, `POST /auth/login`, Rider `/trips` operations and Driver create/read/online/offline/location operations. Requests carry `Authorization: Bearer <access_token>`. Registration takes `username`, `password` (12–1024 characters) and `role`; login takes username/password and returns a 15-minute grant. Spoofable actor/role headers are removed by Gateway and never establish a service principal.

Gateway does not route internal reservation/release/reconciliation, Matching administration or service grants. Direct development service and infrastructure ports bind to loopback; services also authenticate direct HTTP requests. Local Compose HTTP is a trusted development network, not an Internet deployment or TLS acceptance. An external deployment must terminate TLS at its edge, protect service-network access and supply operator-managed keys/secrets. No production signing key is embedded or generated automatically at service startup.

Matching obtains a two-minute service grant from Identity `POST /connect/token` using its configured client credential, and caches it until shortly before expiry. Its only permission is `matching:reserve`, used for Driver reserve/reconcile/read. The Trip service principal has `trip:release` and `matching:manage`. Driver release still requires the exact trip/reservation fencing token. A service credential never replaces domain OCC, receipt deduplication or broker identity. Broker command paths retain the existing authenticated RabbitMQ connection and message contracts.

The shared client reads `Auth__TokenEndpoint`, `Auth__ClientId` and `Auth__ClientSecret`. If no token endpoint is configured it supplies no principal; the real receiving service rejects unauthenticated calls. Lower-layer business fixtures may host endpoints directly to test domain/provider boundaries. They do not establish authentication acceptance.

Trip's bounded Matching-cleanup reconciler reads the authenticated internal endpoint `GET /internal/matching/rounds/{tripId}/{round}/cancellation`. Only the Trip service principal can read it. `STOPPED` requires Matching's committed cancellation tombstone, no READY/IN_FLIGHT/UNKNOWN attempt, and either a terminal round or a durable cancel flag; a tombstone before round intake fences the later intake through its existing shared transaction lock. The response includes the exact trip and round. Trip confirms only that matching-cancellation obligation; release and Payment compensation retain their separate authority proofs. Timeout, denial, malformed/mismatched response or `PENDING` leaves cleanup open for retry. There is no application cross-database query or completion from publish/ACK success.

Run `scripts/test/security-gate.py --identity-tests` against a dedicated Compose project for real Identity/Gateway/service rejection checks and all seven opt-in Identity tests. `scripts/test/core-runtime-gate.py` uses authenticated public ride intake, autonomous Matching and real providers. Its controlled lifecycle actor invokes production Trip handlers for accept/start/complete, whose public HTTP transport is outside the current frozen route set. The script records authority snapshots and final invariant checks; it makes no claim that those lifecycle operations were exposed through public HTTP.

Matching persists the original valid W3C trace parent at production round intake and restores it for autonomous worker execution, including after restart. Existing rounds without context remain valid and start a new trace. Replay never replaces the original parent. The controlled lifecycle actor continues its scenario's trace explicitly; the runtime gate requires the same exported trace to include Gateway, Trip, Matching, Driver and Payment, plus finite samples for required metrics.
